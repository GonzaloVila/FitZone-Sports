# ADR-005 — Framework backend, contenedor de inversión de control y ORM: NestJS, TypeScript y Prisma

- **Estado:** Aceptado
- **Fecha:** 2026-09-02
- **Autor:** Ansaldi Exequiel
- **Sprint:** 1

## Contexto
El desarrollo del backend de FitZone Sports requería implementar una arquitectura modular capaz de gestionar la lógica de 5 módulos funcionales (Usuarios, Gimnasio/Acceso, Clases, Canchas y Pagos), garantizando tipado estricto, desacoplamiento de dependencias y productividad dentro de un equipo de 4 desarrolladores con un plazo de 16 semanas. Se necesitaba una solución que integrara inyección de dependencias robusta de forma nativa y un mapeo objeto-relacional (ORM) moderno que facilitara migraciones reproducibles y consultas tipadas contra PostgreSQL sin incurrir en la verbosidad excesiva de frameworks empresariales tradicionales.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **NestJS + TypeScript + Prisma** | Arquitectura modular nativa con Inyección de Dependencias (IoC); tipado estático extremo de extremo a extremo; soporte oficial de OpenAPI/Swagger; Prisma genera cliente tipado a partir del schema; migraciones declarativas y seguras. | Curva inicial de aprendizaje en decoradores y módulos de NestJS; abstracciones adicionales respecto a Express plano. | **Opción elegida:** Mayor puntuación ponderada (4,90/5) por productividad, modularidad y adecuación al equipo de 4 personas. |
| **Spring Boot + Java + Hibernate** | Ecosistema empresarial sumamente maduro; soporte completo de inyección de dependencias; alto rendimiento en producción masiva. | Curva de aprendizaje más pronunciada; mayor verbosidad de código y configuración; ciclo de compilación más lento; tipado no compartido con el frontend. | Sobrecarga de configuración y menor velocidad de desarrollo para el cronograma del proyecto (puntuación 4,05/5). |
| **Express.js + TypeORM** | Máxima flexibilidad y ligereza; ecosistema amplio en Node.js. | No provee contenedor de inversión de control ni arquitectura modular estandarizada por defecto (exige diseñar la infraestructura desde cero); TypeORM presenta menor estabilidad en migraciones complejas. | Riesgo de arquitectura desordenada y falta de convenciones homogéneas entre los desarrolladores del equipo. |

## Decisión
Se decidió adoptar **NestJS** como framework backend con su contenedor nativo de Inversión de Control (IoC), el lenguaje **TypeScript** y **Prisma** como ORM, fundamentado en la sinergia del tipado estático, la facilidad para estructurar un monolito modular mantenible y la aceleración del ciclo de desarrollo.

## Consecuencias
- **Positivas:**
  - Estructuración modular limpia y desacoplada mediante `@Module` y proveedores con Inyección de Dependencias.
  - Seguridad en tiempo de compilación y autocompletado en consultas a base de datos gracias a Prisma Client generado.
  - Documentación viva de la API generada automáticamente mediante decoradores de Swagger / OpenAPI.
  - Facilidad para instrumentar filtros globales de excepciones (RFC 9457 Problem Details) y validación de DTOs con `class-validator`.
- **Negativas:**
  - Dependencia de la API de Prisma, la cual no modela nativamente ciertas sentencias complejas de PostgreSQL (como constraints de exclusión `EXCLUDE`), requiriendo migraciones SQL manuales en casos puntuales.
  - Sobrecarga en la definición de DTOs y clases de transferencia.
- **Deuda asumida:**
  - El soporte de transacciones anidadas o bloqueos avanzados en Prisma requiere utilizar extensiones de cliente o queries SQL crudas (`$executeRaw`) cuando la abstracción del ORM resulte insuficiente.
