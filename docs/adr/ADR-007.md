# ADR-007 — Estrategia de pruebas, pirámide adoptada y umbral mínimo de cobertura

- **Estado:** Aceptado
- **Fecha:** 2026-11-10
- **Autor:** Ansaldi Exequiel (propuesta, 2026-11-07) · Vila Gonzalo (revisión y aceptación)
- **Sprint:** 6

## Contexto
FitZone Sports concentra reglas de negocio densas: precio dinámico con descuento a socios y recargo en horario pico
(RF-11), vigencia y mora de la membresía (RF-02, RN-03), cancelación de clases con penalidad (RF-07), lista de espera
con notificación (RF-08), pago simulado con comprobante en PDF (RF-13, RF-14), un ingreso validado por un QR que rota
(RF-04) y dos reglas de concurrencia que solo se cumplen si la base las garantiza: un socio no puede estar dentro de dos
sedes a la vez (RN-01) y dos usuarios no pueden reservar el mismo turno de cancha (RN-02). La Unidad V pide una pirámide
de pruebas completa (unitarias, de integración y de extremo a extremo), un umbral de cobertura declarado y una prueba de
concurrencia.

La primera versión de esta decisión (propuesta del 2026-11-07) llamaba «e2e» a las pruebas HTTP con Supertest. Al
crecer, esa capa llegó a 189 pruebas: más que una por requisito, y ninguna pasaba por la interfaz que usa el socio o el
recepcionista. El vértice de la pirámide quedaba más ancho que su medio y la integración real entre el frontend Vue y la
API no estaba probada por nada. Además, el umbral del 60 % estaba declarado pero no configurado: ninguna corrida fallaba
por debajo de él.

Las restricciones eran:
- un equipo de cuatro personas con el desarrollo funcional casi cerrado;
- la entrega el 2026-11-19;
- Windows y Linux en las máquinas del equipo;
- la base de desarrollo compartida en Supabase, que no se podía usar para pruebas que crean y borran datos.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **Pirámide en tres capas: Vitest (unitarias e integración), Supertest (API por HTTP) y Playwright (E2E en navegador)** | Cada capa prueba lo que las otras no ven: lógica aislada, garantías de PostgreSQL, contrato HTTP y el recorrido real del usuario. Playwright abre varios contextos de navegador independientes en un mismo test, lo que permite reproducir dos usuarios simultáneos. También emula la pérdida de red y captura descargas, todo con TypeScript y `async/await`. | Requiere levantar backend, frontend y una base sembrada para la capa E2E. Hay que mantener tres configuraciones de prueba. | **Opción elegida.** |
| **E2E con Cypress** | Muy difundido, con buena documentación y un runner visual cómodo para depurar. | Ejecuta las pruebas dentro de una sola pestaña del navegador, así que no puede manejar dos sesiones independientes a la vez, que es lo que exige reproducir RN-02 con dos usuarios. Usa una API encadenada propia en lugar de `async/await`. La paralelización y el historial de corridas dependen de su servicio pago. | No permite probar desde la interfaz la regla de concurrencia, que es justamente la que la cátedra pide ver. |
| **E2E con Selenium WebDriver** | Estándar histórico, multi-lenguaje y multi-navegador. | No espera automáticamente a que los elementos estén listos: hay que agregar esperas explícitas y las pruebas se vuelven inestables. Requiere instalar y mantener drivers por navegador. Es más verboso y lento que las alternativas modernas. | El costo de estabilizarlo no se justificaba para 17 recorridos y el plazo de entrega. |
| **Considerar E2E a las pruebas HTTP con Supertest (propuesta original)** | Ya existían 189 pruebas, rápidas y estables, contra la app Nest completa y PostgreSQL real. | No pasan por el navegador. Un error en la pantalla, en el router, en el guard de sesión o en el cliente HTTP del frontend no lo detecta ninguna. La capa superior queda más ancha que la intermedia. | No cumple con la definición de E2E de la Unidad V. Esas pruebas se conservan, reclasificadas como «pruebas de API». |
| **Estrategia mayormente E2E (cono de helado)** | Máximo realismo: cada prueba ejercita toda la pila. | Lenta, frágil ante cambios menores de pantalla o de datos, difícil de depurar y poco práctica para cubrir casos de borde como fechas límite o errores 409 y 422. | Desalienta correr la suite a diario. Los casos de borde se prueban mejor y más barato abajo. |
| **Pruebas manuales con Postman o Swagger** | Sin costo inicial de escritura. | No son repetibles, no detectan regresiones y no miden cobertura. | Incompatible con la Unidad V. |

## Decisión
Se adopta una **pirámide de pruebas en tres capas**. Como E2E se elige **Playwright** y no Cypress ni Selenium. El
criterio determinante fue que es la única de las tres herramientas que permite probar RN-02 desde la interfaz, con dos
usuarios reales en navegadores separados reservando el mismo turno a la vez.

| Capa | Herramienta | Dónde vive | Contra qué corre | Cantidad |
|---|---|---|---|---|
| Unitarias, backend | Vitest + mocks | `backend/src/**/*.spec.ts` | Nada externo | 670 |
| Unitarias y de componentes, frontend | Vitest + Vue Test Utils + jsdom | `frontend/src/**/*.spec.ts` | Nada externo | 1254 |
| Integración | Vitest | `backend/src/**/*.integration-spec.ts` | PostgreSQL 16 real en Docker | 82 |
| API por HTTP | Vitest + Supertest | `backend/test/api/**/*.api-spec.ts` | App Nest completa + PostgreSQL en Docker | 189 |
| E2E | Playwright (Chromium) | `e2e/` en la raíz del repositorio | Navegador → frontend → API → PostgreSQL en Docker | 17: uno por requisito (RF-01 a RF-14, RN-01 a RN-03) |

Las capas que tocan la base usan un PostgreSQL efímero (`docker-compose.test.yml`, puerto 55432, datos en memoria), con
el mismo esquema que producción porque se migra con las migraciones de Prisma. Nunca usan la base compartida de
Supabase: la configuración de pruebas aborta si la URL de la base no es local.

La **prueba de concurrencia** está en dos niveles:
- en integración, RN-01 y RN-02 se prueban con intentos simultáneos (`Promise.allSettled`) y después se cuentan las filas
  en la base;
- en E2E, RN-02 se prueba con dos contextos de Playwright que confirman la misma reserva al mismo tiempo.

El **umbral de cobertura** se mide con V8, se muestra como tabla en la terminal y está configurado en Vitest, así que la
corrida falla si se baja de él:
- **Backend, unitarias:** 70 % líneas, 70 % sentencias, 65 % ramas, 60 % funciones. Medido al aceptar: 71,49 / 71,29 /
  66,84 / 64,22.
- **Frontend:** 82 % líneas, 80 % sentencias, 72 % ramas, 72 % funciones. Medido al aceptar: 84,97 / 83,25 / 74,75 /
  75,53.

El umbral se mide sobre las pruebas unitarias. Integración, API y E2E prueban otra cosa (garantías de la base, contrato y
recorrido del usuario), y sumarlas inflaría el porcentaje sin agregar información.

## Consecuencias
- **Positivas:**
  - La pirámide tiene la forma correcta: 1924 pruebas unitarias en la base, 271 en el medio y 17 recorridos E2E en el
    vértice.
  - Las 1924 unitarias corren en segundos y sin Docker, así que se ejecutan a diario.
  - Las garantías que solo existen en PostgreSQL (la constraint de exclusión `exq_reserva_turno` de RN-02 y el índice
    único parcial de RN-01) se prueban contra la base real, no contra un mock.
  - Cada requisito funcional y de negocio queda trazado a un recorrido E2E.
  - Playwright también cubre lo que ninguna otra capa ve: la descarga real del comprobante PDF (RF-14) y el
    comportamiento sin red del puesto de control.
  - El umbral está en la configuración, no solo en este documento: no se puede bajar sin que la corrida falle.
- **Negativas:**
  - Las capas de integración, API y E2E necesitan Docker Desktop abierto y la base de pruebas migrada.
  - La E2E además necesita levantar el backend y el frontend; es la capa más lenta y se corre antes de integrar, no en
    cada cambio.
  - Hay tres configuraciones de Vitest y una de Playwright que mantener.
  - Las pruebas E2E dependen de los textos y roles accesibles de la interfaz: un cambio de etiqueta puede romperlas.
- **Deuda asumida:**
  - La cátedra pide una pipeline que bloquee el merge si la suite falla o la cobertura baja del umbral. La ejecución
    automática en CI queda para la etapa de despliegue (ADR-008); hoy la suite se corre en local.
  - La E2E corre solo en Chromium. Si hiciera falta asegurar Firefox o Safari, Playwright lo permite agregando
    proyectos a su configuración, sin reescribir las pruebas.
  - TDD y BDD, mencionados en la Unidad V, no se adoptaron como metodología: las pruebas se escribieron sobre código
    existente.
