# ADR-007 [A REVISAR] — Estrategia de pruebas, pirámide adoptada y umbral mínimo de cobertura

- **Estado:** Propuesto
- **Fecha:** 2026-11-07
- **Autor:** Ansaldi Exequiel
- **Sprint:** 6

## Contexto
El sistema FitZone Sports posee un conjunto denso de reglas de negocio que abarcan cálculos tarifarios con recargos y descuentos (RF-11), validaciones temporales de mora y vigencia (RF-02), cancelaciones tardías con penalidad (RF-07) y restricciones de acceso concurrentes (RN-01, RN-02). Se requería definir una estrategia de pruebas integral para el backend y frontend (Unidad V) que maximizara la confiabilidad y la detección temprana de regresiones sin degradar los tiempos de desarrollo ni saturar el ciclo de feedback de los desarrolladores.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **Pirámide clásica con Vitest + Supertest y umbral ~60-70%** | Pruebas unitarias co-locadas ultra-rápidas sin base de datos (con repositorios mock); pruebas de integración acotadas contra PostgreSQL real; pruebas e2e sobre endpoints HTTP críticos con base efímera Docker; ejecución paralela rápida con Vitest. | Requiere mantener mocks de repositorios en tests unitarios y sincronizar esquemas en tests de integración. | **Opción elegida:** Mejor equilibrio entre velocidad de feedback en desarrollo diario y validación rigurosa de contratos y concurrencia. |
| **Estrategia basada predominantemente en tests End-to-End (E2E)** | Máximo realismo: prueba toda la pila completa (HTTP, rutas, controladores, base de datos). | Ejecución lenta y pesada; frágil ante cambios menores en esquemas o seed; difícil de depurar; desmotiva la ejecución frecuente en local. | Descartada por ralentizar excesivamente el pipeline y dificultar el testeo exhaustivo de casos de borde lógicos. |
| **Pruebas manuales asistidas por Postman / Swagger** | Cero costo de escritura inicial de código de pruebas; rápido para exploración inicial. | Sin repetibilidad automática; no protege contra regresiones; no cuantifica cobertura de código; viola los requisitos de aseguramiento de calidad de la Unidad V. | Incompatible con los estándares de ingeniería y la entrega del TFI. |

## Decisión
Se decidió adoptar la **pirámide clásica de pruebas** implementada con **Vitest**: una base masiva de pruebas unitarias co-locadas junto al código fuente (`.spec.ts`) sin acceso a base de datos para la lógica de servicios y entidades; una capa intermedia de pruebas de integración (`.integration-spec.ts`) contra PostgreSQL real para validar adaptadores de persistencia; y una capa superior de pruebas End-to-End (`test/e2e/**/*.e2e-spec.ts`) con `supertest` contra un contenedor efímero de Docker, estableciendo un **umbral mínimo de cobertura del 60%** en sentencias y ramas críticas.

## Consecuencias
- **Positivas:**
  - Ejecución de más de 450 tests unitarios en menos de 8 segundos gracias al motor optimizado de Vitest.
  - Aislamiento absoluto de la lógica de negocio frente a la infraestructura externa en las pruebas unitarias.
  - Validación fehaciente de constraints de base de datos (`exq_reserva_turno`) en la suite de integración y e2e.
  - Suite de frontend con más de 980 tests de componentes asegurando la estabilidad visual y funcional.
- **Negativas:**
  - Necesidad de mantener fixtures y factories de datos de prueba (`pagos.fixtures.ts`, etc.).
  - Los tests e2e requieren tener levantado el contenedor Docker local con las migraciones actualizadas.
- **Deuda asumida:**
  - Incrementar progresivamente la cobertura en módulos de reportería compleja a medida que se incorporen nuevos filtros analíticos.
