# ADR-008 — Estrategia de despliegue, contenerización y procedimiento de reversión

- **Estado:** Aceptado
- **Fecha:** 2026-11-11
- **Autor:** Vila Gonzalo
- **Sprint:** 6

## Contexto
FitZone Sports tenía que poder ponerse en marcha de forma determinística en la máquina de un docente o evaluador
(Unidad V, RNF-04). Los lineamientos de entrega fijan dos condiciones de admisibilidad del código:
- un solo comando, `docker compose up --build`, tiene que dejar el sistema operativo y accesible;
- el sistema tiene que traer datos de prueba para al menos 25 sedes, con canchas, clases y usuarios de todos los roles.

La rúbrica de la Unidad V también pide una pipeline que construya, corra la suite y bloquee la integración si algo falla,
y hacía falta un procedimiento de reversión ante un despliegue fallido o una migración que rompiera datos.

La propuesta del 2026-11-07 solo contenerizaba PostgreSQL (`docker-compose.test.yml`); el backend y el frontend se
compilaban a mano con Node en la máquina anfitriona. Esa propuesta:
- tenía cinco pasos, con `sed` y comandos encadenados que no corren igual en Windows;
- apoyaba la reversión en tags de Git, que el equipo decidió no usar hasta la versión 1.0;
- describía la base de pruebas con «volumen persistente», cuando en realidad vive en memoria.

Las restricciones eran:
- un equipo de cuatro con Windows y Linux;
- la entrega el 2026-11-19;
- la base de desarrollo compartida en Supabase, que no se puede exigir para evaluar (cuotas gratuitas, depende de
  internet y de credenciales);
- el repositorio en GitHub.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **Docker Compose con todo el sistema: base, migraciones, backend y frontend en contenedores; CI con GitHub Actions** | Un solo comando en cualquier sistema operativo, sin instalar Node ni PostgreSQL. El orden de arranque se declara con healthchecks. Las imágenes multietapa separan la compilación de la ejecución. El mismo `docker compose up --build` se verifica en cada push. | Hay que tener Docker. La primera construcción tarda unos minutos y las imágenes pesan cientos de MB. | **Opción elegida.** |
| **Docker solo para la base y la app compilada con Node local (propuesta original)** | Imágenes livianas; la app arranca con las herramientas de desarrollo. | Cinco pasos, con `sed` y comandos que dependen del shell. Exige la versión justa de Node en la máquina del evaluador. | No cumple la condición de un solo comando. Se conserva como modo desarrollo, con recarga en caliente. |
| **Máquina virtual o instalación directa, sin contenedores** | Sin capa de virtualización. | Instalar PostgreSQL con la extensión `btree_gist`, crear usuario y base y configurar el servicio a mano. No se reproduce igual en Windows, macOS y Linux. | Propenso a errores y contrario a la condición de admisibilidad. |
| **Despliegue solo en la nube (PaaS como Render o Railway, con Supabase)** | Nada que instalar para evaluar; una URL pública. | Depende de internet, de cuotas gratuitas que se agotan y de credenciales reales que no pueden versionarse. Si el servicio cae el día de la evaluación, no hay sistema. | No garantiza que el docente lo levante sin ayuda. Queda como evolución posible (ver deuda). |
| **Kubernetes (por ejemplo con minikube)** | Escalado, reinicios y despliegues graduales de nivel productivo. | Complejidad muy por encima de cuatro contenedores en una máquina; curva de aprendizaje y requisitos del evaluador mucho mayores. | Desproporcionado para el alcance y el plazo. |
| **CI con Jenkins o GitLab CI en lugar de GitHub Actions** | Herramientas maduras y configurables. | Jenkins requiere un servidor propio que mantener; GitLab CI requiere mover o espejar el repositorio. | El repositorio está en GitHub: Actions corre en el mismo lugar, sin infraestructura extra y gratis para el uso del equipo. |

## Decisión
Se adopta **Docker Compose para todo el sistema** y **GitHub Actions como pipeline de integración continua**. El criterio
determinante fue cumplir la condición de admisibilidad: un solo comando, el mismo en cualquier máquina, que además se
verifica automáticamente en cada push.

**Contenedores (`docker-compose.yml` en la raíz):**

| Servicio | Imagen | Qué hace | Arranca cuando |
|---|---|---|---|
| `db` | `postgres:16-alpine` | Base de datos, con los datos en el volumen `datos-postgres` | — |
| `migraciones` | Etapa `build` del backend | Aplica las migraciones de Prisma (`migrate deploy`). Si la base no tiene ninguna sede, carga el seed de 25 sedes; si ya tiene datos, no lo carga, porque el seed vacía las tablas antes de insertar. Termina. | La base responde (healthcheck) |
| `backend` | Etapa `runtime` del backend (`node:24-alpine`, solo dependencias de producción, usuario sin privilegios) | API NestJS en el puerto 3000 | Las migraciones terminaron bien |
| `frontend` | `nginx:1.27-alpine` con el build de Vite | La SPA en el puerto 8080, con fallback a `index.html` para el router y sin caché para el service worker | El backend responde (healthcheck) |

Los secretos (JWT, clave de cifrado TOTP, contraseña de la base) y las URLs se leen de variables de entorno, con valores
por defecto que solo sirven para una máquina local. Un `.env` las cambia sin tocar el repositorio (ver `.env.example`).

**Pipeline (`.github/workflows/ci.yml`)**, en cada push a `main` y en cada pull request. Cinco jobs:
1. Backend: compilación, tipos de los tests y unitarias con su umbral de cobertura.
2. Backend: integración y API contra PostgreSQL en Docker.
3. Frontend: tipos, unitarias y de componentes con su umbral, y build.
4. E2E: los 17 recorridos de Playwright, después de que pasan los jobs 1 y 3.
5. Despliegue: `docker compose up --build` y comprobación de que la web, el login y las 25 sedes responden.

Los comandos son los mismos que se usan en local (`docs/pruebas.md`).

**Procedimiento de reversión:**
1. **Antes de desplegar una versión que trae migraciones,** respaldar la base:
   `docker compose exec -T db pg_dump -U fitzone -d fitzone > respaldo-AAAA-MM-DD.sql`.
2. **Si la versión nueva falla:**
   - volver el código al último commit sano: `git revert <commit>`, o `git checkout v1.0` desde la entrega en adelante;
   - reconstruir: `docker compose up --build -d`.
3. **Si además una migración dañó datos** (las migraciones de Prisma solo avanzan, no tienen paso atrás automático):
   - restaurar el respaldo sobre una base limpia: `docker compose down -v`, `docker compose up -d db` y
     `docker compose exec -T db psql -U fitzone -d fitzone < respaldo-AAAA-MM-DD.sql`;
   - levantar el resto: `docker compose up --build -d`. Como la base ya tiene sedes, el seed no se vuelve a cargar.

## Consecuencias
- **Positivas:**
  - Un docente con Docker levanta el sistema completo, con datos de 25 sedes, con `docker compose up --build`, sin
    instalar Node ni PostgreSQL y sin configurar nada.
  - El arranque es ordenado y verificable: nada arranca antes de que su dependencia esté sana, y la API no recibe pedidos
    con la base sin migrar.
  - El seed nunca pisa datos: solo se carga sobre una base vacía.
  - Cada push corre las cuatro capas de la pirámide y el despliegue; una regresión se ve en el commit que la introdujo.
  - La reversión tiene pasos concretos, tanto para el código como para la base.
- **Negativas:**
  - Hay que tener Docker; la primera construcción tarda varios minutos y la imagen de migraciones pesa más de 1 GB
    porque incluye las dependencias de desarrollo (el CLI de Prisma).
  - La URL de la API queda fija en el build del frontend: cambiarla obliga a reconstruir esa imagen.
  - El backend en producción con valores por defecto para los secretos solo es aceptable en una máquina local.
  - La pipeline completa tarda varios minutos, sobre todo por el job de E2E.
- **Deuda asumida:**
  - Para que la pipeline **bloquee la integración** hace falta que los cambios entren por pull request, con una regla de
    protección de `main` que exija los cinco jobs en verde. Hoy el equipo integra directo en `main`: la pipeline marca el
    commit en rojo, pero no impide el push.
  - No hay despliegue continuo a un servidor: el sistema se publica corriendo el compose. Un PaaS con base gestionada
    sería el paso siguiente si hiciera falta una URL pública.
  - Los respaldos de la base son manuales. Un entorno real necesitaría respaldos programados y fuera del servidor.
