# ADR-008 [A REVISAR] — Estrategia de despliegue, contenerización y procedimiento de reversión

- **Estado:** Propuesto
- **Fecha:** 2026-11-07
- **Autor:** Vila Gonzalo
- **Sprint:** 6

## Contexto
El sistema FitZone Sports debe poder desplegarse de manera determinística tanto en servidores de producción/evaluación como en las estaciones de trabajo de los evaluadores y docentes (Unidad V, RNF-04). El criterio de aceptación formal exige que un docente pueda clonar el repositorio en una máquina recién formateada y poner la aplicación en funcionamiento en no más de cinco pasos y sin asistencia del equipo. Además, se requería prever un procedimiento formal de reversión (*rollback*) ante eventuales fallos de despliegue o migraciones destructivas de base de datos.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **Contenerización Docker para base de datos + compilación Node local estandarizada** | Aislamiento completo del motor PostgreSQL con sus extensiones (`btree_gist`); puerto parametrizable (`55432`) para evitar colisiones con servicios locales preexistentes; scripts de seed reproducibles; migraciones versionadas y ordenadas temporalmente en Prisma. | Requiere que el entorno host disponga del daemon de Docker y Node.js instalados. | **Opción elegida:** Garantiza la puesta en marcha en 5 pasos exactos sin requerir configurar credenciales remotas ni tocar servicios del sistema host. |
| **Despliegue monolítico en máquina virtual tradicional (Bare-metal / VM sin Docker)** | Acceso directo al hardware sin capas de virtualización de contenedores. | Instalación manual de PostgreSQL, extensiones C, usuario y base de datos propensa a errores humanos; no garantiza reproducibilidad entre distintos sistemas operativos (Linux/macOS/Windows). | Viola el criterio de aceptación del README ("un docente con la máquina recién formateada debe poder levantarlo sin preguntar nada"). |
| **Despliegue exclusivo en la nube (PaaS / Supabase remoto)** | No requiere instalar base de datos local en la máquina de evaluación. | Dependencia crítica de conectividad a internet; riesgo de agotamiento de cuotas gratuitas (free tier); imposibilidad de evaluar la suite de tests e2e aislada de la red. | Incompatible con entornos cerrados o sin conexión estable. |

## Decisión
Se decidió implementar una **estrategia de contenerización híbrida con Docker Compose** para el motor de base de datos PostgreSQL (`docker-compose.test.yml` en puerto `55432` con volumen persistente), combinada con builds optimizados de Node.js/Vite para backend y frontend; y un **procedimiento de reversión basado en tags de Git versionados y migraciones declarativas hacia atrás** mediante `prisma migrate resolve` o scripts SQL de rollback versionados.

## Consecuencias
- **Positivas:**
  - Puesta en marcha garantizada en exactamente 5 comandos copiables y pegables en terminal.
  - Aislamiento total de PostgreSQL en un contenedor efímero que no interfiere con motores existentes en el puerto 5432.
  - Procedimiento de rollback claro: revertir el commit en Git y aplicar la migración anterior del historial.
- **Negativas:**
  - Requiere tener Docker instalado y con permisos de usuario en la máquina host.
- **Deuda asumida:**
  - A futuro, empaquetar también los procesos de backend y frontend en un archivo `docker-compose.prod.yml` multi-stage para despliegues de producción en la nube.
