# ADR-009 — Tratamiento de los medios de pago: tokenización y no persistencia de datos de tarjeta

- **Estado:** Aceptado
- **Fecha:** 2026-09-03
- **Autor:** Vila Gonzalo
- **Sprint:** 1

## Contexto
Las reservas de canchas (RF-13), el cobro de membresías (RF-02) y las penalidades por cancelación tardía de clases (RF-07) deben poder procesarse mediante tarjeta de crédito o débito a través de una pasarela de pago. Dado el alcance académico del proyecto y las estrictas normativas internacionales de seguridad financiera (PCI-DSS), el sistema tenía prohibido bajo cualquier circunstancia almacenar o hacer transitar por sus servidores números de tarjeta (PAN), códigos de seguridad (CVV/CVC) o fechas de expiración en texto plano (RNF-02). Se requería definir el mecanismo de integración con la pasarela para autorizar transacciones de forma segura y trazable.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **Tokenización externa (Mock/MercadoPago / Stripe)** | Cumplimiento total de RNF-02 y aislamiento de PCI-DSS: el cliente tokeniza directo con el proveedor y FitZone solo recibe un token opaco efímero; desacoplamiento de la lógica de cobro mediante adaptador (`PasarelaPagoAdapter`); generación de comprobante y trazabilidad garantizada. | Dependencia de la API del proveedor externo o emulador; flujo en dos pasos (tokenización en frontend y cobro en backend). | **Opción elegida:** Máxima calificación ponderada (4,80/5), asegurando la no persistencia de datos sensibles y total realismo comercial. |
| **Persistencia interna de datos de tarjeta** | Control total sobre los datos y la transacción sin intermediarios. | Incumple de forma flagrante la normativa PCI-DSS y el requisito RNF-02; expone al sistema a gravísimas vulnerabilidades de seguridad y robo de identidad financiera. | **Inadmisible por seguridad** y expresamente prohibido por los requisitos no funcionales del proyecto. |
| **Pago manual exclusivamente administrativo** | Máxima simplicidad técnica; sin pasarela ni tokens. | No permite el autoservicio digital de socios ni la reserva anticipada de canchas en línea; no automatiza cobros de penalidades ni renovaciones. | Incompatible con los requerimientos funcionales del sistema (RF-02, RF-07, RF-13). |

## Decisión
Se decidió implementar un esquema de **tokenización de pagos** mediante una pasarela externa simulada (emulando la API y contratos de MercadoPago/Stripe), donde el frontend envía los datos sensibles directamente a la pasarela para obtener un token de pago opaco y el backend de FitZone Sports procesa el cobro persistiendo únicamente el identificador de transacción y el comprobante PDF, sin almacenar datos de tarjeta.

## Consecuencias
- **Positivas:**
  - Cumplimiento estricto del requisito de seguridad RNF-02 y mejores prácticas de la industria (PCI-DSS).
  - La base de datos de FitZone Sports queda completamente exenta de datos financieros sensibles.
  - Generación de comprobante en PDF con hash de operación para auditoría y respaldo del socio.
  - Facilidad para sustituir el mock por credenciales reales de producción (`MP_TOKEN`) mediante variables de entorno sin modificar el dominio.
- **Negativas:**
  - Requiere un flujo desacoplado en el cliente para obtener previamente el token antes de invocar la API de cobro.
- **Deuda asumida:**
  - En un paso a producción real con procesadores bancarios locales, se requerirá implementar webhooks asíncronos para notificaciones de pagos diferidos (ej. transferencias o pagos en efectivo).

## Requisitos relacionados
RNF-02, RF-02, RF-07, RF-13
