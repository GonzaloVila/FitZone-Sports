# ADR-012 — Patrón Repository como capa de abstracción de persistencia sobre el ORM

- **Estado:** Aceptado
- **Fecha:** 2026-09-03
- **Autor:** Ansaldi Exequiel
- **Sprint:** 1

## Contexto
El backend de FitZone Sports persiste los datos en PostgreSQL mediante Prisma ORM. Para evitar que la lógica de negocio y las entidades de dominio queden fuertemente acopladas a la sintaxis y tipos propios del cliente de Prisma, se requería interponer una capa de persistencia controlada. El objetivo era encapsular las consultas de base de datos, traducir posibles errores específicos del motor relacional a excepciones de dominio comprensibles y posibilitar la ejecución de pruebas unitarias sobre los servicios mediante dobles de prueba (mocks) sin requerir una conexión activa a la base de datos.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| **Patrón Repository (clases concretas / interfaces por entidad)** | Aislamiento entre dominio y ORM; centralización de consultas SQL y mapeos; permite mockear la persistencia fácilmente en tests unitarios; frontera única para traducir errores de base de datos a Problem Details (RFC 9457). | Introduce clases intermedias y código adicional (boilerplate) frente al acceso directo. | **Opción elegida:** Máxima calificación ponderada (4,70/5) garantizando testeabilidad y encapsulamiento de persistencia. |
| **Acceso directo mediante PrismaService en los Servicios de negocio** | Menor cantidad de archivos y clases; llamadas directas más rápidas de escribir al inicio del desarrollo. | Alto acoplamiento: si cambia el modelo de datos o el ORM, se rompen los servicios de dominio; imposible testear los servicios sin levantar la base de datos o mockear la API completa de Prisma Client. | Provoca dispersión de consultas y degrada severamente la mantenibilidad del código. |
| **Active Record (entidades que se persisten a sí mismas)** | Patrón intuitivo común en frameworks como Rails o Django. | Mezcla la lógica de negocio con la lógica de acceso a datos en la misma clase; rompe el principio de responsabilidad única (SRP); no encaja con la filosofía de NestJS ni Prisma. | Rechazado por degradar la arquitectura limpia y modular del sistema. |

## Decisión
Se decidió implementar el **patrón Repository** en todos los módulos del backend (M1 a M5), concentrando las operaciones de consulta y persistencia en clases de repositorio dedicadas e inyectadas por constructor en los servicios de negocio, asegurando que el dominio no conozca los detalles de Prisma ni de PostgreSQL.

## Consecuencias
- **Positivas:**
  - Los servicios de negocio interactúan con métodos de dominio claros (`buscarPorId`, `guardar`, `listar`) sin acoplarse a Prisma.
  - La suite de pruebas unitarias de servicios se ejecuta a alta velocidad en memoria usando repositorios mockeados.
  - Se centraliza el mapeo de errores de unicidad (P2002), registros no encontrados (P2025) y referencias foráneas (P2003) hacia excepciones HTTP estandarizadas.
- **Negativas:**
  - Mayor cantidad de archivos y métodos de delegación.
- **Deuda asumida:**
  - La necesidad de mantener clases concretas de repositorio por cada entidad agregada del sistema.
